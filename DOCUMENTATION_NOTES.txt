1. PROJECT OVERVIEW
------------------------------------------------------------

Project Name:     ReConnect Ethiopia
Type:             Web Application (Full-Stack)
Purpose:          A centralized missing-persons platform for Ethiopia.
                  It connects families, communities, hospitals, and law
                  enforcement through shared information about missing
                  persons, sightings, and unidentified individuals.

Problem Solved:   In Ethiopia, missing person information is scattered
                  across different channels (social media, police
                  stations, hospitals). There is no single place where
                  families can report, search, and receive updates.
                  ReConnect Ethiopia solves this by centralizing all
                  activity in one platform with automatic notifications.

Target Users:
  - Families of missing persons (reporters)
  - General public (sighting reporters, case browsers)
  - Hospitals and police stations (institutional users)
  - Platform administrators

Live URL (Frontend):  https://reconnect-ethiopia-1dza-ashen.vercel.app
Backend API URL:      https://reconnectethiopia-production.up.railway.app

3. DATABASE SCHEMA
------------------------------------------------------------

TABLE: users
  id            INTEGER PRIMARY KEY
  full_name     VARCHAR(150) NOT NULL
  email         VARCHAR(150) UNIQUE NOT NULL
  password_hash VARCHAR(255) NOT NULL
  role          VARCHAR(50)  DEFAULT 'user'
                  Values: 'user', 'admin', 'institution'
  is_banned     BOOLEAN      DEFAULT FALSE
  ban_reason    VARCHAR(500) NULLABLE
  created_at    DATETIME     DEFAULT now()

TABLE: missing_persons
  id                  INTEGER PRIMARY KEY
  full_name           VARCHAR(150) NOT NULL
  age                 INTEGER NULLABLE
  gender              VARCHAR(50)  NULLABLE
  description         TEXT NULLABLE
  last_seen_location  VARCHAR(255) NULLABLE
  last_seen_date      DATE NULLABLE
  status              VARCHAR(50)  DEFAULT 'active'
                        Values: 'active', 'under_investigation',
                                'found', 'closed'
  reported_by         INTEGER FK -> users.id
  photo_url           VARCHAR(500) NULLABLE
  created_at          DATETIME DEFAULT now()

TABLE: sightings
  id                INTEGER PRIMARY KEY
  missing_person_id INTEGER FK -> missing_persons.id
  description       TEXT NULLABLE
  location          VARCHAR(255) NOT NULL
  sighting_date     DATE NULLABLE
  reported_by       INTEGER FK -> users.id
  created_at        DATETIME DEFAULT now()

TABLE: case_events
  id                INTEGER PRIMARY KEY
  missing_person_id INTEGER FK -> missing_persons.id
  event_type        VARCHAR(50) NOT NULL
                      Values: 'report_submitted', 'sighting_received',
                              'status_updated', 'investigation_update',
                              'reunited'
  description       TEXT NOT NULL
  created_by        INTEGER FK -> users.id NULLABLE
  created_at        DATETIME DEFAULT now()

TABLE: notifications
  id                    INTEGER PRIMARY KEY
  user_id               INTEGER FK -> users.id
  notification_type     VARCHAR(50)
                          Values: 'sighting_reported',
                                  'institutional_match'
  title                 VARCHAR(255) NOT NULL
  message               TEXT NOT NULL
  missing_person_id     INTEGER FK -> missing_persons.id NULLABLE
  sighting_id           INTEGER FK -> sightings.id NULLABLE
  unidentified_record_id INTEGER NULLABLE
  is_read               BOOLEAN DEFAULT FALSE
  created_at            DATETIME DEFAULT now()

TABLE: institutions
  id              INTEGER PRIMARY KEY
  user_id         INTEGER FK -> users.id UNIQUE
  facility_name   VARCHAR(255) NOT NULL
  facility_type   VARCHAR(50)  NOT NULL  ('hospital' | 'police')
  region          VARCHAR(150) NOT NULL
  city            VARCHAR(150) NOT NULL
  address         VARCHAR(400) NULLABLE
  contact_phone   VARCHAR(50)  NULLABLE
  status          VARCHAR(30)  DEFAULT 'pending'
                    Values: 'pending', 'approved', 'rejected'
  created_at      DATETIME DEFAULT now()

TABLE: unidentified_records
  id                      INTEGER PRIMARY KEY
  institution_id          INTEGER FK -> institutions.id
  estimated_age_min       INTEGER NULLABLE
  estimated_age_max       INTEGER NULLABLE
  gender                  VARCHAR(20) DEFAULT 'unknown'
  physical_description    TEXT NULLABLE
  found_location          VARCHAR(255) NOT NULL
  found_date              DATE NOT NULL
  condition               VARCHAR(50) DEFAULT 'unknown'
                            Values: 'conscious', 'unconscious',
                                    'stable', 'critical', 'deceased',
                                    'in_custody', 'unknown'
  notes                   TEXT NULLABLE
  photo_url               VARCHAR(500) NULLABLE
  status                  VARCHAR(30) DEFAULT 'open'
                            Values: 'open', 'identified', 'closed'
  matched_missing_person_id INTEGER FK -> missing_persons.id NULLABLE
  created_at              DATETIME DEFAULT now()
  updated_at              DATETIME DEFAULT now()

TABLE: alembic_version
  version_num VARCHAR(32) PRIMARY KEY
  (Used internally by Flask-Migrate to track migration state)

5. USER ROLES & PERMISSIONS
------------------------------------------------------------

GUEST (not logged in):
  - Browse all missing persons
  - View individual case details and sightings

REGULAR USER (role: 'user'):
  - Everything guests can do
  - Report a missing person (with photo)
  - Report a sighting
  - View personal dashboard with stats
  - Receive notifications (sightings on own reports, institution matches)
  - Apply to register as an institution

INSTITUTION USER (role: 'institution', institution.status: 'approved'):
  - Login → redirected to Institution Dashboard (not user dashboard)
  - Submit unidentified individual records (no personal info)
  - View and manage their own submitted records
  - NOT able to report missing persons or sightings

ADMINISTRATOR (role: 'admin'):
  - Access dedicated Admin Panel (completely separate UI shell)
  - Manage all missing person reports
  - Manage all sightings
  - Manage all users (ban/unban, role changes)
  - Approve/reject institution registrations
  - View all unidentified records
  - View all case events and activity history
  - View platform-wide statistics

BANNED USER (is_banned: true):
  - Cannot log in (403 error with reason shown)
  - Admin can unban at any time

7. KEY FEATURES IN DETAIL
------------------------------------------------------------

A. SMART MATCHING ENGINE
   - When an institution submits an unidentified record, the backend
     immediately runs a scoring algorithm against all active missing
     person cases.
   - Scoring weights:
       Age match:         30%
       Gender match:      25%
       Location match:    30%
       Description match: 15%
   - Cases scoring >= 38/100 trigger a notification to the family.
   - Uses Python difflib.SequenceMatcher for text similarity.
   - Results include match score (0-100) and human-readable reasons.

B. NOTIFICATION SYSTEM
   - Two trigger events:
     1. Someone reports a sighting on a case → reporter notified
     2. Institution submits a record that matches a case → reporter notified
   - Notifications show in a bell dropdown in the user Dashboard.
   - Unread count badge updates every 60 seconds (polling).
   - Notifications link directly to the relevant case page.
   - Users can mark individual or all notifications as read.
   - Users can dismiss/delete notifications.

C. INSTITUTION CONNECT FLOW
   1. Hospital/police staff creates a normal user account.
   2. They go to /institutions/register and submit facility info.
   3. Admin reviews and approves in the Institutions admin panel.
   4. Once approved, the user's role becomes 'institution'.
   5. Their navbar dropdown shows "Institution Dashboard" instead of
      the regular dashboard.
   6. They submit unidentified individual records (physical description
      only — no name, ID, or personal information required).
   7. System automatically matches records against missing persons.
   8. Families receive notifications for potential matches.

D. AUTHENTICATION
   - JWT Bearer tokens stored in localStorage.
   - Tokens include expiry (exp claim) decoded client-side.
   - ProtectedRoute and AdminRoute components check expiry on
     every page navigation — expired tokens are cleared automatically.
   - Banned users receive a 403 response on login with the ban reason.

E. IMAGE UPLOAD
   - Accepts: JPG, JPEG, PNG, WEBP only
   - Maximum size: 5 MB
   - Custom drag-and-drop ImageUpload component with:
       - Preview after selection
       - Remove button
       - Format and size hint text
       - Drag-over highlight state
   - Uploaded files stored in Backend/app/static/uploads/

F. INTERNATIONALISATION
   - Full translations for all 13+ pages in English and Amharic.
   - Language toggle: pill button fixed bottom-right on every page.
   - Preference saved to localStorage, persists across sessions.
   - Translation files: src/locales/en/ and src/locales/am/

G. DARK / LIGHT MODE
   - Toggle button fixed bottom-right alongside language toggle.
   - Preference saved to localStorage.
   - Implemented via data-theme="dark" on <html> element.
   - All page CSS files have [data-theme="dark"] override blocks.
   - Admin shell is natively dark regardless of theme.

12. KNOWN LIMITATIONS & FUTURE IMPROVEMENTS
------------------------------------------------------------

CURRENT LIMITATIONS:
  1. No real-time notifications (uses 60s polling instead of WebSockets)
  2. No email notifications — only in-app bell notifications
  3. Photo matching is description-based (text similarity) not AI/facial
  4. No pagination on large result sets (all records loaded at once)
  5. API URLs are environment-variable based but require manual
     redeploy when changed
  6. No password reset / forgot password flow implemented

SUGGESTED FUTURE IMPROVEMENTS:
  1. WebSocket notifications using Flask-SocketIO for real-time alerts
  2. Email/SMS notifications via SendGrid or Africa's Talking API
  3. AI-based photo similarity matching for better unidentified records
  4. Pagination and infinite scroll for missing persons list
  5. Map view showing last-seen locations using Leaflet.js
  6. Mobile app (React Native) using the same Flask API
  7. Case sharing via WhatsApp / Telegram integration
  8. Multi-language support beyond Amharic (Oromo, Tigrinya, Somali)
  9. Password reset flow via email OTP
  10. Audit log for all admin actions
  11. Bulk import of missing person reports via CSV
  12. Public API for third-party integration with NGOs and media

13. HOW TO RUN LOCALLY
------------------------------------------------------------

REQUIREMENTS:
  - Python 3.11+
  - Node.js 18+
  - PostgreSQL running locally

BACKEND SETUP:
  cd Backend
  python -m venv venv
  .\venv\Scripts\Activate.ps1          # Windows
  pip install -r requirements.txt
  copy .env.example .env               # fill in DATABASE_URL etc.
  $env:FLASK_APP = "run.py"
  flask db upgrade
  python run.py
  # Runs on http://127.0.0.1:5000

FRONTEND SETUP:
  cd reconnect-frontend
  npm install
  copy .env.example .env               # set VITE_API_BASE=http://127.0.0.1:5000
  npm run dev
  # Runs on http://localhost:5173

CREATE FIRST ADMIN:
  After registering an account, run in PostgreSQL:
  UPDATE users SET role = 'admin' WHERE email = 'your@email.com';
